# 共包控制与同步：功能完成路线

更新：2026-11-04。目标是在连续广播的**同一个 secondary PDU** 内，让 BLE 与 IEEE 802.15.4 两条独立接收链分别取得本侧命令和共同时间语义，并完成粗粒度的软件定时控制。射频接收率优化与可靠性扫描暂缓；功能验收可先使用确定性测试向量、保存的 IQ 和离线回放。功能正确不等于无线可靠、独立设备绝对同步或物理执行器同步。

## 现状和缺口

| 环节 | 已有能力 | 尚缺的功能 |
| --- | --- | --- |
| 发送 | `b2z_control_start?` 在每轮重复同一任务，双侧 35 B 记录共用一个 224 B secondary；`slot_index` 逐时隙递增 | 一轮内多个不同 `command_id` 的任务和明确的每任务重发计划；可审计的逐任务发送记录 |
| BLE 接收 | `exadv_rx/receive.py` 恢复完整 PDU、CRC、AD 与本地 IQ 采样位置；离线匹配器解析 `B2 43` | 实时控制记录解析与逐命令状态事件；接收时校验包内 Run ID，避免归档标签与实际包不一致 |
| IEEE 802.15.4 接收 | `zigbee_rx/control_receive.py` 实时独立解码、校验、统计重复时隙 | 与 BLE 共用的时间估计、命令判决和软件处理语义 |
| 离线分析 | `control_match/analyze.py` 做双侧逐时隙匹配；`sync_replay.py` 用历史包拟合时间映射并在后续共同包上验证 | 将时间估计用于命令的接受、有效期、计划和软件处理；区分逐任务结果与逐发送尝试结果 |

现有 `sync_replay.py` 是批量回放分析，不是在线调度器。现有同频 ch39 发射的 AuxPtr 与实际 secondary 不一致，只能称为同频诊断共包，不能据此宣称完整 exadv 跟随。`ref_tick_ms` 指计划的 secondary 前导码起点，实际空口起点尚未校准。

## 下一项实现：单侧时间与命令处理模块

先在 `python/control_match/` 实现一个**按本侧已解码记录和本地 IQ 样本进度驱动**的模块，再由 BLE、IEEE 802.15.4 接收脚本分别接入。对调用者只暴露两个操作：`observe(record, packet_start_sample, available_sample)` 输入一个本侧有效包，`advance(current_sample)` 推进本侧采集进度并返回事件。输入记录必须由本侧 PHY 和应用校验独立得到；模块不得从另一接收链补字段。使用同一接口做离线回放与实时接收，避免两套状态规则分叉。现有逐包 JSONL 没有解码时的 `available_sample`；回放这项功能时应重新流式解码保存的 IQ，或在新接收记录中补存该字段，不能把包起点冒充命令可用时刻。

模块内部有两部分：

1. **本地时间模型**：将包内 `ref_tick_ms` 映射到本侧的 IQ 样本索引。BLE 标记取 BLE 前导码起点；IEEE 802.15.4 标记先减去已知的包内位置差，换算到同一设计参考点。记录实际训练包、跨度、最近更新时间、拟合速率、残差和随失更年龄增长的不确定度。一个包只能估计偏移并采用标称采样率；多个不相邻包可估计速率。每次更新只使用当时已到达的包；异常时隙和离群点必须有明确拒绝记录。**计划发送时刻到实际 RF 起点的未知偏差单列**，不藏入“同步精度”。
2. **命令状态机**：以本侧配置的发送源、`run_id`、`command_id` 和本侧角色为任务键。`flags=0` 仅更新模型；重复命令可更新模型，但只能产生一次软件处理。先检查版本、应用校验、目标、操作码、时间质量和一致的任务字段，再决定 `accepted`、`duplicate`、`wrong_target`、`unsupported`、`expired`、`late` 或 `time_quality_insufficient`。`valid_until_ms` 是最迟接受时刻，`execute_at_ms` 是目标处理时刻；判断当前时刻应使用**包可用时的采集进度**，不能倒用包起点。接受后按估计的本地目标样本索引调度；后续时间更新可在预定冻结窗口前修正目标，冻结及取消规则需要记录。超过有效期或误差界时，不补执行。

软件动作先用每侧独立的 `NOOP`、`SET_STATE(value)`、`TRIGGER(code)` 适配器实现。它们只改变或记录主机软件状态，不代表商用设备命令或物理执行器动作。每条任务保存 `decoded → accepted/rejected → scheduled/cancelled → software_processed` 事件，包含本地样本索引、时间模型版本、估计误差界、原因和处理时刻。实时处理还需另存单调主机时钟与队列延迟；两台 HackRF 的样本零点和两进程墙钟不得直接相减。

### 这一项的验收

- 同一份记录可离线回放，也可由两个实时接收脚本各自输入；同输入产生相同命令判决和任务事件。旧 `B2 5A` 性能帧及其 Sequence 规则不变。
- 使用单包、非相邻包、连续漏收、重复广播、乱序、错误目标、未知命令、迟到、过期、失去时间质量、不同双侧参数等测试向量，逐项检查状态和事件。重发次数不能增加逻辑任务数。
- 以保存的独立 IQ 做功能回放，明确哪些结果是本侧软件处理，哪些只是基于样本索引的模拟处理；不输出未经校准的双机执行时差。

## 随后的功能顺序

| 顺序 | 实现内容 | 可检查的交付物 |
| --- | --- | --- |
| 2 | BLE 实时 `B2 43` 接入；将现有 IEEE 802.15.4 实时接收器接入同一命令处理模块 | 两侧分别输出逐任务事件 JSONL/CSV、异常原因和可读报告；归档 Run ID 与包内 Run ID 不符时明确报错或标记 |
| 3 | 板端增加一轮内的任务计划：多个 `command_id`、每任务重复 K 次、可穿插纯时间更新；全轮 `slot_index` 连续、相同命令重发保持标识 | 计划清单、逐任务和逐时隙板端计数；单任务旧命令保持兼容；每个事件仍只有一个数据 secondary |
| 4 | 双侧任务汇总与功能对照：分别报告解码、接受、计划软件处理和实际软件处理；同一批 IQ 回放“立即处理”与“时间模型处理” | 逐任务四象限、重复/过期/迟到/失去时间质量计数；一次发送和 K 次重发按任务分母分别统计 |
| 5 | 发送侧提供“BLE 与 IEEE 802.15.4 分别发送”的对照路径；修正共包模式 AuxPtr 与实际 secondary 的时频声明并单独验证 | 相同任务和截止时间下的发送次数、primary/secondary 及全部 RF 时长预算；固定 secondary 功能验证与规范 exadv 跟随分别标注 |

第 3 项要先定义一份小型任务计划，再启动板端；一轮的时间域和 `run_id` 保持不变，`command_id` 随任务改变。现有 ZigBee `ControlTracker` 只允许一轮有一个任务字段组合，届时须改为按任务键分别维护状态。不要把每次重发算成新任务。第 5 项的跨信道跟随可能受现有 HackRF 调谐和两接收机分工限制；发送声明正确、固定频点独立解码和完整跟随必须分别验收。

## 功能完成后再开展的实验

恢复射频条件后，按[下一阶段计划](next_stage_plan.md)做容量、联合可靠性、同步误差、控制效率和公平基线扫描。条件样本的时间残差与全部计划任务的成功率分别报告；未校准板端实际 RF 起点、两机采集零点及主机处理延迟之前，只能报告软件原型和相对预测结果，不能报告物理同步执行精度。
