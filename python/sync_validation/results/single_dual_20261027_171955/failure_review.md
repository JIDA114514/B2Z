# Run 10271：双台阶段的 USB 运行时断连

日期：2026-10-27。本轮与上轮“启动时找不到设备”不同：两个阶段预检查都检测到两台 HackRF，BLE 设备在双台采集中途断开并重新枚举。设备枚举成功只说明检查时可访问，不能保证持续采集过程中不掉线。

## 错误时间线

- 双台接收开始于本地时间约 17:20:26，BLE 设备末尾为 2926a0c3。
- BLE 前约 15 s 持续传输约 16 MB/s，随后 1 s 无数据，报告 `Couldn't transfer any bytes for one second.`。
- 停流及关闭时返回 `No such device`，这是数据中断后的后续错误。
- 内核日志在 **17:20:41** 明确记录 `usb 1-3.2.2: USB disconnect, device number 55`。
- 紧接着同一路径重新枚举为设备 56，序列号仍为 2926a0c3。

因此已确认 USB 设备发生断开/重新枚举。仅凭这份日志不能区分线缆接触、hub/端口/供电、设备或固件重启、人工操作等具体根因。不能把 `hackrf_close()` 当成最早错误，也不应通过屏蔽关闭错误或自动重连拼接 IQ 来“修复”这轮实验。

## 接收状态与比较边界

| 阶段 | ZigBee 有效唯一包 | 时长 | 状态 |
| --- | --- | --- | --- |
| single_before | 2 | 30 s | complete |
| dual | 5 | 约 16.29 s | BLE 故障后协调停止，interrupted |
| single_after | 未运行 | — | 未完成 |

BLE 双台片段约 14.975 s，243 个 BLE CRC 有效包中 241 为 primary、2 为 secondary。BLE 应用队列最高 2/64、ZigBee 最高 3/64，没有报告应用队列溢出，不支持把本次传输停止归因于 Python 队列满。

双台阶段被截断，不能用 5 包与单台 2 包直接比较为性能改善或下降。单台阶段本身也只有 2 包，因此当前不支持“仅双台运行才造成低接收率”的结论。USB 稳定性问题与目标信号解码质量应分别排查。

这组短测未复现故障，支持其具有间歇性，不证明硬件链路已经稳定，也不能宣称 4 Msps 比 8 Msps 更可靠或简单判定带宽超限。需要在发生故障的原有采集流程下继续验证。

## 下一步操作

当前两台设备仍在同一 USB2 hub 下，路径为 `1-3.2.2` 和 `1-3.2.3`。优先将 BLE 设备移出当前共用 hub，使用可靠数据线直连主机，记录新 USB 拓扑后重测；不要只在同一个 hub 上换孔后假定已获得独立总线。按条件尽量分配独立 USB 总线，官方同步检查表也要求关注多设备 USB 共享和 shortfall。

若仍断连，逐项交换 USB 数据线、主机接口、设备角色，判断故障是否跟随设备或连接路径。每次只改变一个条件并记录，先取得完整、无断连的采集，再评价 RF 解码或同步。不要在当前证据下直接刷写固件或修改解调码本。

可在用户终端监视 USB 事件：

```bash
journalctl -k -f
```

必要时按系统权限使用 `sudo journalctl -k -f`。关注 `usb 1-...` 的 disconnect/reset/重新枚举信息。
