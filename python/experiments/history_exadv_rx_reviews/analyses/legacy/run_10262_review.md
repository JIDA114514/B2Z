# Run 10262 实时接收检查

板端命令：`bluebee_exadv_perf_start?30 200000 60 10262`。默认 realtime，整轮计划 300 个时隙。接收记录：`rx_20261026_152018_750312`，当前版本启用 1 kHz 连续 IQ 直流抑制，Fs=8 Msps，ch39，LNA=24 dB，VGA=20 dB，RF amp 关闭。

|---|---:|

| 总 CRC 有效 exadv PDU | 636 |
| 匹配目标 primary | 143 |

104 个目标 secondary 均为 172 B PDU payload。将 BLE 去白化后的 BlueBee 区域还原为空口映射字节，并按板端符号表反解，全部恢复出 30 B 测试负载；Run ID、10 B 测试头、确定性填充和 IEEE 802.15.4 FCS 全部正确。这里是对 BLE 已成功恢复内容的二次校验，不是独立 ZigBee 接收机验证，也不是双接收端联合成功率。

首尾目标 secondary 分别为 IQ 起点后 0.0397665 s 和 29.839223 s。按序列与采样时间线性拟合，时隙间隔约 199996.459 us，序列 0 的 secondary 约位于采集开始前 4.360 s。因此接收仅覆盖 60 s 板端实验中间的 30 s。69.33% 是序列范围覆盖率，不是无线 PRR；没有对齐窗口的 tx_completed 时无线 PRR 为 N/A，也不能用整轮 300 个计划包作为本次分母。

按接收进程完整 30 s 采样观察窗口，30 B 测试 payload gross throughput 为 832 bit/s（104 byte/s）；扣除 10 B 头的 application goodput 为 554.667 bit/s（69.333 byte/s）。这是当前接收窗口结果，不能替代完整 60 s 实验结果。

## 实时处理

正常完成，采集 480000000 字节，处理 240000000 个复采样，应用队列高水位 2/64，无应用队列溢出。每块跨度 8.192 ms，处理均值 4.980 ms、P99 6.293 ms、最大 13.180 ms。没有持续处理积压证据；偶发超出块时长由队列吸收。不据此保证 USB/硬件完全无丢样。

与上一轮 Run 10261 的 DC 修复离线结果 99/150=66% 相近；本轮是修复代码实时结果，确认修复实际生效，但不能把单次约 3.33 个百分点差异当作稳定改善，更未达到 99% 目标。

## 时序与 AuxPtr

对能找到 100 ms 内前序目标 primary 的 100 个 secondary，诊断 start-to-start 时间为 30801.5–30811 us，中位数 30808 us，比 AuxPtr 声明的 30000 us 多约 808 us。此计算使用同一 IQ 的相对采样时间，仅为同频时序诊断，不是规范事件配对或已校准绝对精度。板端在 primary DMA 提交前取软件时间，再等待至截止点并提交 secondary DMA，需后续校准实际空口时刻与软件调度的偏差，不能直接把软件时间当空口时间。

原有 AuxPtr 仍声明 ch3、PHY=1，而实际 secondary 在 ch39 以 1M 波形发射；matched_events=0 符合严格匹配规则，不能解释为没有收到 secondary。

## 离线诊断对照

- 同一份完整 30 s IQ，将同步门限从 0.84 降到 0.70，目标 secondary 仍为 104；目标 PDU 集合完全一致：True。本轮剩余丢包不能靠简单降低门限解决。
- 对首 5 s IQ，仅在独立诊断进程将内部解调采样率从 2 Msps 提高到 4 Msps，目标 secondary 从 13 到 14；只是局部诊断，尚不足以据此更改正式接收配置。
- 未修改本轮原始结果，未调整发送端和正式接收参数。
