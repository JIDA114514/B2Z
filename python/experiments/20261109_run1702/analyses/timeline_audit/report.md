# Run 1702：独立接收与 IQ 时间轴质量审计

分析日期：2026-11-09。数据源为两块 HackRF 的**独立实时采集**、[板端最终统计](../../board.board.log)和[逐槽 CSV](timeline.metrics.csv)；板端行由用户在对话中提供，不是串口终端完整原始文件。结构化结论和事件文件 SHA-256 见[审计 JSON](audit.summary.json)。当前板端仍为 `rf_mode=same_channel_diagnostic`。

## 解码结果

| 指标 | 结果 | 说明 |
| --- | ---: | --- |
| 板端计划 / 到达 / 生成 / primary DMA 完成 / secondary DMA 完成 | 300/300，各阶段 | `deadline_miss=0`、`dma_timeout=0`；DMA 完成不是实测 RF 起点。 |
| BLE 目标 secondary | 299/300 | 时隙 198 未恢复；BLE 另恢复 299 个短 primary，`packets=598` 不能当成 598 个控制尝试。 |
| IEEE 802.15.4 有效应用记录 | 299/300 | 时隙 42 未恢复；其余通过 PHY FCS 和应用校验。 |
| 两侧同一时隙共同有效 | 298/300 | 仅 BLE：时隙 42；仅 IEEE 802.15.4：时隙 198；两侧均无：0。 |

两接收器的 `run_id=1702` 一致，各录 80 s、读取 1,280,000,000 字节并正常结束；接收队列没有报告溢出。由于另一侧分别收到时隙 42 和 198，本轮 300 个计划 secondary **均有至少一条独立空口解码证据**。结合板端最终计数，缺失不能解释为这两个时隙完全未发。

## 时间轴异常

对每侧有效控制包，计算相邻可见时隙的 `本地 IQ 样本差 / 8 Msps − 槽号差 × 200 ms`。这一诊断只检查采样时间轴连续性，不将两台 IQ 的绝对起点直接相减。

| 接收侧 | 槽区间 | 相对计划间隔偏差 | 伴随现象 |
| --- | --- | ---: | --- |
| IEEE 802.15.4 | 41→43 | −55.197 ms | 时隙 42 缺失；从 43 起在线时间模型出现 `clock_outlier`。 |
| BLE | 197→199 | −131.819 ms | 时隙 198 缺失；从 199 起在线时间模型出现 `clock_outlier`。 |
| BLE | 199→200 | −21.987 ms | 再次出现明显采样时间压缩。 |
| IEEE 802.15.4 | 199→200 | −78.612 ms | 再次出现明显采样时间压缩。 |

两侧同一包的**采样索引差相对时隙 0 的变化**在 41→43、197→199、199→200 分别跳变 +55.909、−131.072、+56.625 ms；这是时间轴诊断，不是同步算法误差。其余连续片段内该差值缓慢变化，按三段分别拟合得到约 1.28、1.33、1.35 ppm 的相对斜率，仅用于区别突跳与平滑漂移，不能当作经过校准的时钟精度。

实验后对 IEEE 802.15.4 HackRF（序列号尾部 `3348a6c3`）运行只读 `hackrf_debug -S`，设备报告 **2 次 shortfall**、最长 **1,266,432 字节**，按 8 Msps、2 字节/复采样换算为 **79.152 ms**；这与 199→200 的约 78.612 ms 压缩相近。BLE HackRF（尾部 `2926a0c3`）的旧固件返回 `feature not supported`，故没有同类设备计数；其 IQ 时间轴自身仍显示异常。该状态查询是在采集结束后进行，未在采集前重置计数，因此只作为支持证据，不据此精确分配每一次缺样。HackRF 官方指出 RX shortfall 会造成样本缺失并破坏同步。[HackRF 同步检查清单](https://hackrf.readthedocs.io/en/stable/synchronization_checklist.html)

当前 `lsusb -t` 显示两块 HackRF 同处 Bus 001 的 480M USB 2.0 总线上，IEEE 802.15.4 设备还经过两级 hub。主机 HackRF 工具为 2026.01.3，BLE 设备固件为 2021.03.1，IEEE 802.15.4 设备固件为 2023.01.1。共享总线、hub 和固件差异是需控制的采集条件，**不能仅凭这些信息证明单一根因**。

## 对同步结论的影响与下一步

现有[冻结模型初步回放](../holdover_cut20_preliminary/sync.report.md)把训练槽限定在 `<20`，随后在整个后半轮计算误差；其约 56 ms 的中位绝对差主要受上述采样时间轴跳变支配，**不能报告为广播同步机制的精度或漂移**。对全部 300 槽的共同解码率 298/300 仍是可用的共包功能结果；两者的证据资格不同。本轮也没有实测板端 RF 起点或物理执行事件。

先把接收时间轴修好，再按[预注册方案](../../../../../doc/independent_sync_holdover_experiment_plan.md)做失更与周期更新分析。建议保持馈线、板端 200 ms/300 槽和接收增益不变，**先只把两条接收命令的采样率同时降到 4 Msps**，使用新的 Run ID；两条解码器均支持这一采样率，双设备原始数据率由 32 MB/s 降为 16 MB/s。新轮仍保存 IQ、板端完整日志，结束后立即查询可用设备的 `hackrf_debug -S` 并重算逐槽样本间隔。若仍有毫秒级跳变，再调整 USB 连接，使设备避开级联 hub 或使用不同主控制器，并单独验证；仅仅换到同一控制器的另一个插孔不能证明总线已分离。只有两侧样本时间轴在整轮内连续，才计算同步保持误差。
