# 连续单包双协议粗粒度同步与简单控制：下一阶段计划

制定日期：2026-10-30。研究目标是在**连续广播的每个事件中，只使用一个 secondary `AUX_ADV_IND`**，让 BLE 与 BlueBee/IEEE 802.15.4 两条独立接收链分别恢复控制命令和同一时间语义。允许重复广播同一任务，但不能把多个 secondary 或链式 PDU 算作一个包。空口成本计入各事件的 primary、secondary、失败尝试和重发。现阶段的“控制”以软件命令解析及调度事件为对象；没有独立执行器测量前，不报告物理同步执行成功率。

本计划依据[设计与先例研究](sync_control_payload_research.md)及现有[同 IQ 验证工具](../python/sync_validation/README.md)。已有性能测试头和 Sequence 规则保持兼容，新控制格式另行版本化。

## 1. 先固定可检验的主张

1. **共包**：两侧从同一 secondary 独立恢复各自完整字段，完成校验，再用 `(run_id, command_id)` 关联；任一侧不能借用另一侧解码结果。
2. **漏包后仍可更新**：每个计划广播时隙有序号和名义周期；接收端利用不相邻的有效包估计时间关系。板端实际发射抖动、漏发及 BLE 广播时序变化必须记录或纳入误差预算，不能把 `序号 × 名义周期` 直接当成实际空口时间。
3. **粗粒度同步**：两侧分别将命令映射到共同的轮次时间域，并给出估计误差与过期判据。建议预先以 50 ms 为主要候选容差，同时报告 10/100 ms 敏感性；这些是待验证目标，不是现有精度。独立 HackRF 的采集起点不同，需先校准，不能直接比较两个文件的 `sample_time_s`。
4. **简单控制**：先选一个可审计的软件命令，例如 `SET_STATE(value)` 或 `TRIGGER(code)`；报告正确解析、去重、迟到、过期与计划时刻的软件处理。无执行器或硬件事件测量时，不能把处理事件称为物理动作。

## 2. 工作包与进入下一步的条件

| 阶段 | 主要工作 | 交付物与进入下一步的条件 |
| --- | --- | --- |
| P0：接收链基线 | 用现有性能帧做单台—双台—单台对照，核对板端计划/完成计数、两份 IQ 的目标包、采集完整性、RF 配置和样本率；必要时逐项交换天线、线缆或 USB 路径。 | 同一轮保存板端统计、两侧逐包记录和诊断报告；至少确认两块 HackRF 在双台工作条件下均能独立恢复目标 secondary。若一侧持续为零，先定位接收条件，暂停双端同步精度结论。 |
| P1：冻结 v1 字段 | 先写字段表、字节序、单位、溢出规则、两侧封装、校验及命令状态机；逐字节核算扩展头、AD、BLE 控制区、原始 802.15.4 字节和 BlueBee 映射后字节。校正并核实 AuxPtr 的 PHY/信道/偏移编码。 | 版本化格式说明、编码/解码测试向量、单个 PDU payload 不超过 255 B 的预算和容量边界；确定一条与旧性能协议分开的板端启动路径，不改旧 Sequence 语义。 |
| P2：同 IQ 共包原理验证 | 先离线生成并发射 v1 波形，在同一 IQ 上分别运行 BLE 与 IEEE 802.15.4 解码。按已解析布局补偿两种前导码的固定包内位置差。注入漏收、重复、过期和不支持命令案例。 | 逐计划时隙四象限结果、字段一致性、误码/校验失败、去重判决和容量扫描；时间参考验证明确标为“共同 IQ/时钟”，不推断独立设备同步。 |
| P3：双 HackRF 连续广播 | 固定可接收的 secondary 频点，连续发送多个计划时隙；两个进程各自保存 IQ、解码和命令事件，之后才按命令标识合并。扫描间隔、命令长度、重复次数 K 和执行提前量。 | 至少三轮交替顺序的独立实验；每轮报告两侧成功、仅一侧成功、均失败、重复、迟到与过期。分母为计划任务数，重发不增加任务数；附板端计数、USB/主机丢样检查及 IQ 关键片段。 |
| P4：时间模型与软件调度 | 以 secondary 明确的 PHY 边界为参考，区分生成、DMA 提交和空口发送时间。用预先划定的校准段估计固定偏置及采样率/时钟漂移，再在未参与拟合的时段检验；测试连续漏收后的误差增长和失去同步时的拒绝规则。 | 报告偏差、中位数、P95、P99、最大值、CDF、样本数与缺失数，并将校准不确定度单列。无外部共同时间基准时，报告相对预测残差及其界限，不声称绝对时钟误差或物理执行时差。 |
| P5：公平对照与完整 exadv 验证 | 相同任务、RF 条件、截止时间和重发规则下，对比“分别发送”“共包立即处理”“共包加时间模型”；计入全部空口发射。另验证 primary、AuxPtr、实际 secondary 的时频一致和接收跟随能力。 | 联合命令解析成功率、请求至软件完成时延、单位成功任务空口成本及置信区间；区分固定 secondary 验证和完整 exadv 跟随。若当前 HackRF 调谐速度不支持跨信道跟随，就明确把该能力留作未验证边界。 |

P2 可在 P0 诊断期间推进离线设计与实现；P3 和 P4 的独立设备结论依赖 P0 的双端有效接收。P5 的比较不预设共包一定优于分别发送。

## 3. v1 格式设计时必须回答的问题

- **标识**：两侧分别携带 `version`、`run_id`、`command_id`、目标设备或组、命令类型与参数。每个计划时隙另有 `slot_index`；同一命令重发保持 `command_id`，物理尝试单独计数。旧性能协议的 Sequence 仍按计划时隙递增，不复用为命令编号。
- **时间**：明确共同 epoch、secondary 空口参考点、`slot_index` 与计划/实际发射时刻的关系、目标时刻、有效期及量化单位。两侧可采用不同字节编码，但必须还原同一语义；普通 IEEE 802.15.4 接收端不会解析 BLE AuxPtr。
- **状态**：规定首次有效命令、重复、过期、迟到、未知版本、未知目标、未知命令、单侧漏收和失去时间参考时的行为。单向广播没有接收确认，也不承诺两侧原子执行。
- **边界**：原始 802.15.4 命令长度、BlueBee 后的 BLE 字节数和全部重复开销同时记录；46 B 是旧性能命令上限，不能直接当作新共包容量。

## 4. 数据与判定口径

每次实验保存配置、代码/固件版本、完整板端命令和最终计数、两侧原始逐包/逐命令结果、采样率与中心频率、时间参考定义、处理异常、摘要 CSV/JSON、报告及关键 IQ。沿用 `python/experiments/YYYYMMDD_run<run_id>/` 归档，新增联合分析放入该轮 `analyses/`。将请求、解码、软件处理和实际动作分成不同事件；不存在的动作事件记为缺失。

核心结果至少同时给出：`双方正确解析 / 计划任务`、四象限计数、一次发送与 K 次重发的差异、截止时间内结果、全部 RF 发射时间 / 成功联合任务，以及时间误差的条件样本数和缺失数。分母为零写 `N/A`。粗粒度容差的通过数也以**全部计划任务**为分母，同时另报仅在双方有效包上的条件时间误差，避免丢包被隐藏。

## 5. 最近一个可执行动作

先用[单台—双台—单台脚本](../python/sync_validation/README.md#单台双台接收控制实验)复测现有性能帧，结合板端最终统计确认两条独立接收路径的目标包。随后完成 v1 字段表和单包预算，再动板端和接收器实现。板端裸机源码目前未被 Git 跟踪；修改后在本仓库检查逻辑与语法，实际 SDK 构建和上板由用户执行。`app_FreeRTOS/` 的修改需要同步到 SDK 实际编译目录后再验证。
