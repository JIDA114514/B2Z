# Run 1701：馈线连接后的双接收端评估

实验实际采集于 2026-11-09；目录名日期沿用旧命名。用户将无线连接改为馈线连接，具体线缆、分路和衰减配置未记录。对照使用 [run 1601 无线实验报告](../../../20261104_run1601/analyses/multi_task_review_1601/report.md)；两轮接收设备角色、8 Msps、2480 MHz、LNA 24 dB、VGA 20 dB、30 s 均一致。板端最终统计仅有 1601 轮，本轮未提供。

## 结果

| 指标 | 1601 无线 | 1701 馈线 | 口径 |
| --- | ---: | ---: | --- |
| BLE 独立接收，目标 secondary | 9/9 | 9/9 | 1701 另有 9/9 个短 primary；同频诊断配对，不是跨信道跟随。 |
| ZigBee 独立接收，FCS 与应用记录有效 | 2/9 | 9/9 | 1701 实时原始包的包内 `run_id` 均为 1701。 |
| 两侧同一时隙均有效 | 2/9 | 9/9 | 按 `run_id` 和时隙 0–8 逐条匹配，不相乘边际接收率。 |
| 两侧均恢复的非零控制任务 | 1/2 | 2/2 | 命令 43、44 各按任务去重，三次重发不增加任务分母。 |

1701 的 BLE [实时摘要](../../captures/ble/rx.summary.json)和[逐事件](../../captures/ble/rx.control.events.jsonl)完整恢复时隙 0–8。ZigBee [实时摘要](../../captures/zigbee/rx.summary.json)显示 9 个 FCS 正确、9 个应用记录有效，但该进程误用 `--run-id 1601`，故全部记录为 `foreign_control`，`unique=0`。[原始逐包记录](../../captures/zigbee/rx.packets.jsonl)显示九个包均为 `run_id=1701`、时隙 0–8；以正确 ID 对同一 IQ 的[完整离线回放](../corrected_run_id/zigbee/rx.report.md)得到 9/9 唯一有效时隙、无重复和乱序。保留误配置的实时报告，不能将离线回放当作第三台接收机或新一次发射。

两条实时采集均正常结束，分别读取 480,000,000 字节、处理 30 s IQ，队列未报告溢出。ZigBee 侧原始 IQ 的 `clipped_components=0`；BLE 侧为 36,770，都是量化端点计数而非校准的射频饱和判据。没有板端 1701 最终计数，也没有 USB 采样缺口的独立证明，因此这里报告的是按预设九个计划时隙的**联合有效解码**，不是已核准发射分母的无线 PRR。

## 判断边界

保持原设备分工时，将连接改为馈线后，原 ZigBee HackRF 的有效记录从 2/9 提升到 9/9。这说明该接收链在当前条件下能够完整解码共包，前两轮的低接收数不能单独证明 HackRF 硬件故障。馈线同时改变接收电平、传播环境和可能的连接附件，现有记录无法把改善归因到其中某一因素，也不能据此预测无线环境下的稳定接收率。

两侧实时软件控制均未提供已校准的时间参考误差界；命令 43、44 虽被两侧解析，仍按规则以 `time_quality_insufficient` 拒绝，没有软件处理完成事件，更没有物理执行或跨设备同步精度测量。下一步若要定位无线低接收率，固定其余参数，仅交换天线/馈线或两设备位置，并记录衰减、连接图和板端最终统计。
