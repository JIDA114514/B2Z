# 双独立接收端的时间参考保持实验方案

状态：2026-11-09 制定；1702 已执行但时间轴不连续，1703 以事先说明的 **4 Msps** 修订采样率重测，1704 和 1705 再次复测。结果见 [三轮阶段复核](holdover_1703_1705_review.md)。本方案检验两条独立 SDR 接收链利用一串单 secondary 共包时间更新，在收到不同更新包或长期失去更新后，对共同发送时间参考的估计能否保持一致。当前测量对象是**时间参考估计**，不是软件命令处理时差、物理执行器动作或绝对空口发射时间误差。

## 1. 实验问题与固定条件

- 发送端为现有 Zynq/AD9363 板；BLE HackRF A 与 IEEE 802.15.4 HackRF B 各自录制并独立完成 CRC/FCS 和应用校验。只在两侧解码后按 `run_id`、`command_id=0`、`slot_index` 关联。不得把一侧数据注入另一侧解码器。
- 先采用 1701 轮已验证可双侧完整解码的馈线拓扑；记录分路、线缆长度、衰减、板端功率和两侧增益。运行前确认 HackRF 接收口的输入功率不超过官方给出的 -5 dBm 上限，必要时加入外部衰减。[HackRF One 规格](https://hackrf.readthedocs.io/en/stable/hackrf_one.html) 馈线是受控链路条件，结果不称无线传播可靠性。固定当前 `rf_mode=same_channel_diagnostic`，不称规范跨信道 AuxPtr 跟随。
- 本轮只发 `command_id=0` 的纯时间更新，不安排定时控制任务。固定 `period_ms=200`、300 个计划时隙，总板端计划时长 60 s；槽号 `s` 的共同字段应满足 `ref_tick_ms=200×s`（单位 ms）。计划数在板端 1024 槽、600 s 上限内。
- 两接收器均使用 8 Msps、2480 MHz、LNA 24 dB、VGA 20 dB、AMP 关闭；保留 IQ 和完整逐包记录。各录 80 s，给人工启动与结束留余量。ci8 预计每侧约 1.28 GB，两侧约 2.56 GB；运行前核对磁盘空间和 USB 总线。
- 1702 的 8 Msps 录制出现几十毫秒级采样时间轴跳变。重测 1703 前已决定两侧改为 4 Msps，以降低 USB 负载；其他包计划、预留验证槽和分析策略保持本方案定义。1703 每侧录得 640 MB IQ。采样率修订必须与原方案一同披露，不能把 1702 和 1703 的同步误差直接合并。
- 以一个新 `run_id` 关联本轮，例如 `1702`。**两条命令和板端必须使用同一个 ID**；先核对终端启动行，避免 1701 轮 ZigBee 侧误填 ID 导致的 `foreign_control`。

## 2. 操作步骤

先在板端准备计划，不启动：

```text
b2z_plan_clear?
b2z_plan_add? 0 300 0 0
```

在项目根目录打开两个终端，分别启动接收器。下例使用未占用的 `run_id=1702`；实际操作时可换成其他未用过的 ID。两条脚本默认按**各自启动时的本地日期**与 Run ID 自动归档到同一个 `python/experiments/YYYYMMDD_run1702/`，并分别建立带唯一后缀的 `captures/ble/`、`captures/zigbee/` 子目录。因此通常不需要 `EXP_DIR` 或 `--experiment-dir`。

```bash
python3 python/exadv_rx/receive.py \
  --run-id 1702 --channels 39 \
  --control-target-id 1 --duration 80 --quiet
```

```bash
python3 python/zigbee_rx/control_receive.py \
  --run-id 1702 --channel 26 \
  --expected-packets 300 --control-target-id 2 --duration 80 --quiet
```

两个接收器尽量在 5 s 内先后启动；确认两侧均开始采集，且显示的 `run_id`、序列号、频率、增益符合计划后，在较晚一侧启动后的 5 s 内输入：

```text
b2z_plan_start? 1702 200
```

仅当两侧**启动时刻**可能跨本地午夜，或需要预先固定归档位置时，才给两条命令同时加上相同的 `--experiment-dir python/experiments/<日期>_run1702`。显式目录模式直接使用 `captures/ble/rx.*` 和 `captures/zigbee/rx.*`，重做一轮须换新的目录或 Run ID，避免与已有文件冲突。采集过程跨午夜但两侧在同一天启动，不影响自动归档。

将**完整串口输出**保存为本轮 `board.board.log`，包括 `CONTROL_PLAN_START/ENTRY/STATS/TASK/SLOT`，不要只保存最终汇总。接收结束后检查两个摘要的 UTC 采集区间均覆盖全部 0–299 槽。此轮没有非零控制任务，接收器不出现软件处理事件是预期行为。

## 3. 预先固定的数据划分

首先保留两端实际独立解码到的有效槽集合，统计 300 个计划槽的“两侧、仅 BLE、仅 IEEE 802.15.4、两侧均无”。以下分析对真实有效记录施加**离线观察掩码**，模拟漏收和失去更新；掩码造成的缺失必须与实际 RF 漏收分开保存。验证包由离线评估器读取，但视为在线时间模型不可用的探针，不能声称接收端在真实漏包期间观察到了这些包。

- 初始训练候选为 0–19 槽。训练包数 `N=1,2,5,10`，表示每侧拟合时使用的**最近 N 个有效更新时间包**，不是 RF 重发数。
- `common`：两侧都从偶数槽 `0,2,...,18` 中取最后 N 个作为初始训练。`disjoint`：BLE 仍取这些偶数槽，IEEE 802.15.4 改从奇数槽 `1,3,...,19` 取最后 N 个；两侧训练包身份完全不重合。缺少所需有效包时该配置记为训练不足，不从验证区补包。
- 固定验证集合 `V={s | 20≤s<300 且 s mod 5∈{2,3,4}}`，共 168 个计划槽。所有方案使用相同 V；任何验证包的时间字段和接收时刻**都不参与任何模型拟合**。只有两侧均独立收到的槽才有条件误差，缺收仍留在 168 的分母和四象限计数中。
- `freeze`：初始训练后完全停止模型更新，用 V 检查长达约 56 s 的失更保持能力。
- `periodic`：分别设计划更新间隔 `U=1,5,10 s`，对应 5、25、50 槽。`common` 两侧候选更新槽均为 `20+m×(U/0.2)`；`disjoint` 的 BLE 使用这些槽，IEEE 802.15.4 使用其后 1 槽。候选更新槽与 V 不相交。某侧实际没收到候选更新时，该侧跳过更新，保留旧模型并记录真实失更年龄；另一侧不得替其更新。每次只用本侧此前最近 N 个有效更新点重拟合。
- 同时报告 `N=1` 的偏移模型（速率取标称 8 Msps）与 `N≥2` 的偏移＋频率模型。所有策略、槽集合、失败处理和分位数定义在看结果前固定，不根据验证误差挑选训练槽或调参。

早期 [`sync_replay.py`](../python/control_match/sync_replay.py)只完成单个切分点的初步回放；正式固定验证集、周期更新和逐槽结果现由 [`holdover_analyze.py`](../python/control_match/holdover_analyze.py)生成。旧输出继续标为“单切分初步回放”，不能与后者混用。

## 4. 估计量与统计口径

BLE 标记为其前导码起点；IEEE 802.15.4 标记为嵌入帧前导码起点。当前包布局给出的设计位置差为 472 µs，先按布局从 IEEE 802.15.4 本地标记扣除，布局变动时重新解析，不用验证包拟合这项差值。两台 IQ 的采样零点不同，**不能直接相减原始 `sample_start` 或主机墙钟**。

对每侧单独拟合 `local_time = a + b × ref_tick_s`。`N=1` 时 `b=1`，其余配置用该侧已许可的历史更新包拟合 `a,b`。对共同收到的验证槽 `s`，分别用该侧的本地包标记反算 `estimated_ref_s`；定义 `relative_error_us = (estimated_ref_ble_s - estimated_ref_zigbee_s) × 10⁶`。同一验证包仅用于**验算**，不重新估计 `a,b`。另报每侧 `estimated_ref_s - ref_tick_s`，但该值包含板端计划到实际 RF 的误差，不能命名为纯时钟误差。

每个方案至少输出：训练槽和跨度、实际更新槽、最近更新时间、模型斜率 ppm、全部 168 个验证槽的双方有效状态、两侧有效槽数、共同有效槽数；在共同有效的条件样本上输出有符号偏差、绝对误差中位数/P95/P99/最大值、CDF，以及误差随失更年龄的散点和分箱。预登记 10 ms 为本原型的**相对估计容差**，同时报告 1、5、20 ms 灵敏度；阈值内数量必须给出“共同有效验证槽分母”和“全部 168 个计划验证槽分母”两个版本，后者把漏收计为未达标。分母为零时写 `N/A`。

板端 `ref_tick_ms` 绑定**计划 secondary 前导码起点**，`secondary_dma_late_us` 是计划到 DMA 提交函数返回，不是实测 RF 起点。初始拟合会吸收固定收发路径与馈线延迟；本实验测的是在该校准条件下**两侧相对时间参考估计的一致性和保持**。它不能给出独立设备的绝对时钟同步误差、真实执行时差或板端空口起点误差。两块 HackRF 的共享频率参考和共同启动是不同的硬件条件，本轮不假定具备任何一个。

## 5. 有效性检查与归档

- 板端最终 `planned_slots=reached_slots=generated=primary_completed=tx_completed=300` 且 `deadline_miss=dma_timeout=0` 为完整发送代理条件；若不满足，逐槽标出板端异常，不能将其误判 RF 丢包。即使满足，DMA 完成也不是完整空口发射的直接证据。
- 两份接收摘要必须 `status=complete`，各自处理 80 s IQ；核对捕获字节数、队列溢出、量化削顶、`rx.hackrf.log` 和设备可用时的 USB shortfall。HackRF 官方指出不同设备没有共享时钟时采样率可不同、没有硬件触发时起点不一致，短采样也会破坏连续时间轴。[HackRF 同步检查清单](https://hackrf.readthedocs.io/en/stable/synchronization_checklist.html)
- BLE 侧逐槽核对 CRC、共包结构、包内 Run ID、ADI/DID 与槽号；IEEE 802.15.4 侧独立核对 PHY FCS、应用 CRC、Run ID、槽号和周期。出现不一致、捕获未覆盖整轮、队列溢出或已知 USB shortfall 时保留诊断数据，不给该轮时间精度结论。
- 保存实际命令、完整板端日志、馈线连接图和参数、两台设备序列号、固件/脚本版本、两侧完整 JSONL 与摘要、关键 IQ 的 SHA-256、预设掩码清单、逐槽 CSV、逐方案 JSON/CSV 和图。目录日期与真实 UTC 采集时间分别记录；大型 IQ 留本机，Git 中保留哈希、配置、可复核样本及结果表。

本方案完成后，论文可报告“受控馈线条件下，两台独立接收设备对同一板端广播时间参考的估计保持与不同包训练效果”。如要进一步声称**空口绝对同步精度或同步执行**，还需独立校准板端实际 RF 起点、两台采集时钟/起点、固定接收延迟，并测量真实处理或执行事件。当前同频调试波形也不证明规范的 BLE secondary 跟随；Bluetooth 对 `AUX_ADV_IND` 的 secondary 信道有明确规定。[Bluetooth LE 说明](https://www.bluetooth.com/bluetooth-le-primer/)
