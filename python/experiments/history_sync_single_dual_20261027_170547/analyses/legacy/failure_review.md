# 单台/双台对照中止诊断

本次原始摘要和 IQ 未修改。单台阶段正常完成 30 s，Run 10270 恢复 56 个唯一有效 ZigBee 测试包，队列最高 5/64。

切换双台阶段时，BLE 子进程的原始错误为 `hackrf_open() failed: HackRF not found (-5)`，不是解码失败或 Resource busy。随后协调脚本停止另一接收进程，避免把只有一台运行的阶段当作双台实验。

双台阶段 ZigBee 只采集约 0.360448 s、恢复 1 包后被中止，该数量不能与完整 30 s 的 56 包比较；第三个单台阶段没有执行。因此本轮尚不能判断双设备活动是否导致目标包下降。

事后执行 `hackrf_info` 只检测到 `000000000000000017c467dc3348a6c3`，未检测到 BLE 所需 `000000000000000017c467dc2926a0c3`。当前能确定第二台未被系统识别，无法仅凭日志确定是拔除、USB 连接/供电异常还是其他枚举问题。

此前工具缺少设备预检查，导致完成首段才暴露第二台不可用。已修正 `capture_single_dual.py`：

- 每个阶段开始前检查两个完整序列号，缺失时不启动该阶段的接收。
- 明确两台设备在单台阶段也须保持 USB 连接，只切换接收进程活动。
- 子进程失败时直接显示 HackRF 原始原因和日志路径。
- 在失败阶段也保存两侧子进程摘要及退出码，顶层报告标记 error。

新增缺失设备预检查、枚举解析及失败原因保留回归，与已有测试合计 10 项通过。修复未运行新的 RF 实验；需恢复第二台枚举后再重做三阶段。若板端还在持续发送，先手动 `bluebee_perf_stop?`，准备新一轮时使用与脚本一致的新 Run ID。
