# Run 1101 双接收诊断

本轮只使用 Run ID 1101、Command ID 43 的两份独立 HackRF 采集。Run 1100 因环境干扰排除。原始逐包记录和接收摘要分别位于 `captures/ble/` 与 `captures/zigbee/`；加入后补板端日志的正式逐时隙匹配见 `../control_match_with_board/control.slots.metrics.csv`。

## 有效解码

两份采集均正常处理 40 s、320,000,000 个复采样（标称 8 Msps），分别使用不同 HackRF 序列号。BLE 侧恢复 52 个通过 CRC、扩展头、应用 CRC16 和字段校验的控制时隙；ZigBee 侧恢复 74 个通过 FCS、应用 CRC16 和字段校验的控制时隙。二者共同恢复 52 个，只有 ZigBee 恢复 22 个，只有 BLE 恢复 0 个。两侧共同时隙的共享字段全部一致，重复均为 0。

板端最终统计已由用户补充并保存到 `../../board.board.log`：100/100 个计划时隙完成生成、primary 和 secondary DMA，`deadline_miss=0`、`dma_timeout=0`。因此本轮 BLE 有效解码 / DMA 完成为 52/100，ZigBee 为 74/100，**逐发送时隙**的联合有效解码为 **52/100**；仅 BLE、仅 ZigBee、两侧均缺分别为 0/100、22/100、26/100。100 次广播重复的是同一个 `run_id=1101, command_id=43` 逻辑任务；任务层面仅有 **1/1 个任务**被两侧至少各恢复一次，不能用这 1 个样本估计任务可靠性。DMA 完成是发射代理量，不能单独证明全部完整空口发射，也不能排除接收处理损失。BLE 报告中的 653 是所有 CRC 正确的 BLE 广播包，其中 601 个为 primary，52 个为本轮 secondary 控制包，不能把 653 当作控制接收数。严格 AuxPtr 匹配为 0，同频诊断配对为 36；这轮是同频共包诊断实验。

按 20 个计划时隙分组，BLE / ZigBee / 双侧共同有效数分别为：0–19：11/15/11；20–39：11/15/11；40–59：11/14/11；60–79：13/17/13；80–99：6/13/6。BLE 最长缺失为时隙 90–98（9 个），ZigBee 最长缺失为 3 个。两侧采集队列没有报告溢出，设备日志没有显式错误；这不能排除 USB 丢样或无线损坏。

## 两条 IQ 时间轴的留出检查

仅作采样时间轴稳定性诊断。对于 52 个共同收到的时隙，取两侧 `sample_start / 8e6` 的差。它包含不同的采集起点、包内 BLE/ZigBee 前导码位置及固定接收路径延迟，**绝对差值不能解释为同步误差**。按时隙排序，用最早 20 个共同包（时隙 0–36）拟合此差值随 `slot_index` 的直线，在剩余 32 个共同包（时隙 38–99）检验。拟合吸收固定差值及相对线性采样率差；没有使用检验包重新对齐。

- 首末共同包的原始时间差为 2.22419075 s 和 2.22419975 s，相差约 9 μs。
- 校准段估计的两接收采样时间轴相对速率差约 0.479 ppm。
- 32 个留出包的绝对残差：中位数 0.241 μs，P95 0.499 μs，P99 0.520 μs，最大值 0.524 μs。

这些残差衡量 **用共同包校准后，同一次 RF 事件在两条采样时间轴上的相对稳定性**。它们尚未评估两侧独立用各自收到的不同控制包估计共同 epoch，也未测实际命令执行时差。P99 只有 32 个留出样本，不能作为稳定尾部界。板端 `ref_tick_ms` 是计划的 secondary 起点；其相对实际发射时刻的偏差尚未校准。

板端 `secondary_dma_late_samples=100`、最大 80,334 μs、平均 80,142 μs。这是计划 secondary 起点到 DMA 提交函数返回的迟到统计，不是逐包实际 RF 起点；约 80 ms 的系统迟到需要在评估相对板端时间误差前校准。下一步实现时间模型的离线回放：每侧独立选用 1/2/4/8/16 个历史有效包训练，只在时间上更晚且未参与训练的共同包上计算两侧时间估计差；另扫描连续漏收和更新时间间隔。至少再做两轮有效独立重复。
