# N4：单 secondary 容量、legacy 对照与适用范围

状态：2026-11-12 板端 v2 格式与容量串口接口已实现并完成本地检查，主机双端接收与单轮分析已适配，上板验证和跨配置汇总待完成；接口见第6–7节，逐步操作与15点命令清单见第8节。

## 1. 推进依据与待补项

2203 已完成修改后 300 槽固定频点双端初验；2204 完成新版 BLE 跟随能力审计，91/120 槽跟随、BLE 三命令均恢复。同轮 IEEE 数据未归档，按用户决定将其补采/联合验证移至后续独立重复阶段；不能写成 N3 完整双端验收已完成。此缺项不阻塞 N4 设计和实现。补采必须有同轮两侧数据，不能将不同轮次拼成联合结果。

N4 回答：同一 secondary 可以承载多少两侧应用数据；边界内是否均能独立恢复；相同任务与时间语义下，legacy 需要多少帧、重复及重组成本。无执行器、共享时钟或 RF 起点测量条件，不评估物理执行精度、绝对同步、实测能耗或严格空口间隔。

## 2. 格式与字节预算（实现前冻结）

当前 v1：扩展头含长度字节10 B、Flags AD 3 B、厂商 AD 长度/类型/Company ID 4 B、BLE记录35 B、IEEE记录35 B。IEEE PHY额外8 B（前导/SFD/PHR及FCS），BlueBee映射比例4:1，映射区172 B，PDU payload合计224 B。PDU头、BLE前导/AA/CRC不包含在255 B payload上限内。此预算以当前生成器布局为前提，每轮须导出实际字节验证。

已实现并冻结的 v2 最小变长方案如下，保持 v1 与旧性能命令兼容：

|记录偏移|长度|含义|
|---|---:|---|
|0–32|33 B|沿用 v1 核心字段位置，version=2；包含 run、slot、时间语义和本侧命令|
|33|1 B|本侧扩展数据长度 n|
|34…|n B|本侧扩展数据|
|34+n|2 B|应用CRC16，覆盖此前全部34+n字节，小端；算法沿用v1|

每侧长度36+n。IEEE另计算完整PHY FCS，BLE另计算完整BLE CRC。未知版本、长度不一致、CRC错误、超容量必须拒绝；不能截断数据或自动改用链式广播。扩展数据用于容量探针，可视为应用blob的完整传递，不能将填充数据宣称为已有执行器命令功能。两侧使用不同确定性内容（包含侧别、run和slot作为生成种子），独立解码后比较实际恢复字节；预期内容绝不能补写到解码结果中。生成算法见第6节，本地测试向量由C生成器与主机解析器交叉检查。

令 b、z 分别为 BLE/IEEE 扩展数据字节数，则在保留当前封装时：

- B=36+b；Z=36+z（Z不含PHY FCS）。
- BlueBee区域=4×(Z+8)=176+4z。
- PDU payload=49+B+4Z=229+b+4z ≤255，即 b+4z≤26。
- v2零扩展229 B；v1参考224 B。两者有5 B格式开销差，不能直接归因于RF可靠性变化。
- IEEE映射起点=17+B=53+b（相对PDU payload起点）；LE 1M下本侧已知标记位置差=(7+53+b)×8 µs。布局改变必须重算，不沿用v1的472 µs。

这是当前格式的编码容量，不是已测容量。每个配置分别输出应用扩展字节、固定命令/时间字段、应用CRC、PHY/FCS、映射字节、AD与扩展头。同步时间字段重复承载的成本必须明确；不得把全部36 B都称为应用净数据。

## 3. 实验矩阵与顺序

先完成离线预算、边界拒绝、CRC与双协议同IQ验证，再用两台HackRF独立录制。板端使用跨信道模式1、primary ch39/secondary ch3；BLE固定ch3、IEEE固定ch12，4 Msps，沿用已验证接线、LNA16/VGA10、amp关闭。固定接收用于隔离负载影响，不称为完整跟随容量测试。

### A：格式与结构验证（不增加物理轮次数）

枚举所有合法整数(b,z)，导出PDU和IEEE帧，独立解析与校验；覆盖PDU长度254/255/256附近、长度字段错误、坏CRC及截断。非法点应在发射前被明确拒绝，无DMA提交。记录哪些限制来自单PDU、AD长度、PHY长度或当前实现缓冲区。若生成器限制先于255 B，记录真实限制，不静默降低测试长度。

### B：首轮空口扫描

每配置100个不同command_id任务、每任务一次发送(K=1)，slot继续按物理计划槽递增。首轮固定周期500 ms，发包50 s，两侧各录制80 s；两端启动后及时发送并检查首末槽均在记录窗口内。若长负载触发生成超时，保留结果，另用较长周期为全部比较配置开新组，不能只修改失败点的周期后混合比较。

推荐扫描15个合法点：

- z=0，b∈{0,8,16,24}；
- z=2，b∈{0,8,16}；
- z=4，b∈{0,8}；
- z=6，b=0；
- 精确边界(b,z)∈{(25,0),(26,0),(18,2),(10,4),(2,6)}。

另做一个v1工作点参考。RF矩阵未测区域留空，不插值为成功；大于容量区域标结构不允许。每个网格点独立run_id，建议2301起按生成清单分配，先检查编号占用。不要手写一串未经实现的串口参数。

长度上界外例子(27,0)、(3,6)、(0,7)只做拒绝验证。首轮扫描后按预设规则选零扩展、BLE最大边界、IEEE最大边界及失败边界点；这些点后续安排至少3轮独立重复，交替顺序。单轮100包不用于宣称高可靠性保证。

### C：legacy同任务对照

首先完成可行性和编码表，再选择少量代表点上板。不得把当前35 B记录大于31 B当作legacy无法实现同任务的证据。

对照必须保留本侧目标、命令及完整参数、run/command关联、参考时间、有效期、去重和截止规则；允许压缩字段或配置会话上下文，但需说明取值范围、冷启动/失更依赖，并计入上下文分发和更新成本。

至少分析两种实现：①同语义紧凑编码，检查是否能单帧承载；②无法单帧时分片并重组，明确片号、总长、任务标识、完整性校验和过期清理，只有完整恢复才计成功。legacy AdvData按31 B核算，另计AdvA、PDU头、前导/AA/CRC；片头、Flags、Company ID等均扣除。若BlueBee不能在单个legacy载荷中独立恢复完整IEEE命令，评估IEEE侧可解析的分片或独立IEEE发射基线，报告架构差异；不得把BLE分片拼接后当作IEEE接收成功。

先比较同应用任务/K/截止期的完整波形与发送次数，再增加同提交有效波形预算的尝试次数对照。共包计入primary+secondary，legacy计入每个广播信道副本、所有分片、上下文和重复，失败尝试也计入。单SDR只能顺序发射，不假设双发射机并行。可以复用N2分别发送基线，但必须适配变长内容后再测。

若legacy物理实现尚不可用，输出分析预算与不可实现约束，并标记“未实测”；不能将其画成实测性能曲线。N4整体交付仍需说明实际完成到哪一层，预算结果不能替代公平对照的RF证据。

## 4. 指标与归档

逐槽输出两侧完整内容/CRC、run/slot/command、双方成功/仅BLE/仅IEEE/双方失败；逐任务关联而非将两侧概率相乘。给出联合有效解析数/计划任务数、有效解码数/DMA完成数（代理口径）、去重和缺失原因。生成失败、DMA失败、捕获截断、未定位候选分别标注，不统一归为无线丢包。

报告字节预算表、联合解析率热力图和容量边界；所有比率含分子分母，0分母为N/A。成本报告全部相关提交有效波形时长/成功联合任务数，同时报告每任务发送次数、分片数和跨度；零样本padding单列，包间静默不计作RF占用。时间只用同一本地样本域的片间/重组间隔或清楚标注的主机软件耗时，不计算未校准双端执行时差。

IQ原始文件、接收参数、完整串口日志、版本/源码哈希、输入任务清单和两侧独立恢复字节必须保存。使用experiments/YYYYMMDD_runID，分析放analyses/n4_capacity/；跨配置清单记录(b,z)、格式、PDU实际字节数、时间映射、固件、K、周期、截止期、接线及异常。分析不得覆盖历史v1结果。

## 6. 板端接口与冻结格式（2026-11-12）

板端已实现，主机v2接收与单轮分析已适配（见第7节）。新增命令严格接受5个十进制整数：

```text
b2z_capacity_start? <run_id> <period_ms> <attempts> <ble_extra_len> <ieee_extra_len>
```

例如零扩展与单PDU上界（应分别运行，先检查run_id未占用）：

```text
b2z_capacity_start? 2301 500 100 0 0
b2z_capacity_start? 2302 500 100 26 0
b2z_capacity_start? 2303 500 100 2 6
```

run_id=1..65535，period_ms=500..65535，attempts=1..1024，attempts×period_ms≤600000。b≤26、z≤6、b+4z≤26，否则启动前拒绝且不提交DMA。不接受负数、小数、十六进制、缺参或额外参数。固定模式1（joint ch3），K=1。使用bluebee_perf_status?查询、bluebee_perf_stop?提前停止；与旧性能/control/plan共享busy互斥。不读取或修改手工暂存plan。

每槽动态生成任务，无须plan_add：slot_index从0起，command_id=slot_index+1；BLE target/opcode/arg=1/1/1，IEEE=2/1/2。ref_tick_ms=slot×period_ms，valid_until_ms=ref_tick_ms+2000，execute_at_ms=ref_tick_ms+3000。此为容量探针的命令语义，并不表示板端或接收器已执行。失败槽仍消耗槽号和command_id。v2格式按第2节冻结；接收端必须显式识别version=2，不能将35 B v1 CRC规则直接套用。

扩展数据算法冻结为无符号32位LCG：side=1表示BLE，side=2表示IEEE；初值 `0xB2430200 ^ (run_id << 16) ^ slot_index ^ (side * 0x9E3779B9)`，乘法按32位回绕。每字节先更新 `state=state*1664525+1013904223`（模2^32），再取最高8位。应用CRC16沿用v1 CRC-CCITT，初值0xffff，覆盖核心、长度及全部扩展，CRC以小端写入。IEEE另有PHY FCS；内容预期仅用于独立解码后的校验。

启动输出CAPACITY_START与CONTROL_PLAN_START/ENTRY；状态和结束输出CAPACITY_CONFIG，逐槽CAPACITY_SLOT输出本槽实际构建的两侧记录、映射及PDU payload长度，built=0时长度为0而非有效零长度包。CONTROL_PLAN_TASK/SLOT、CONTROL_BURST/COST及CONTROL_TIME记录继续输出。长度与容量元数据和各槽内容在RF调度结束后输出，避免逐槽串口打印扰动发送。配置预算与实际PDU长度不符则拒绝本槽发射。

复用已有任务调度、缓存前移、主动轮询与超时处理；没有新增发射线程，也不改变v1和旧性能命令。源码已同步SDK实际编译目录。ARM语法检查（取时开/关）以及v1/v2生成器、边界/CRC/映射、虚拟任务序列测试通过；尚未构建上板。更新后的接收和单轮联合分析器支持v2；旧版本脚本会拒绝v2。下一步为上板空口初验及跨配置manifest扫描、热力图工具。

## 7. 主机接收与单轮联合分析（2026-11-12）

已适配：exadv_rx/receive.py、zigbee_rx/control_receive.py、std_ble/verify_board_exadv.py与control_match/plan_analyze.py。v1/v2按包内版本自动识别，无须额外指定长度；BLE按本侧长度定位记录并检查总封装/映射区预算，IEEE仅解析本侧PHY负载，完整应用CRC与本侧确定性扩展内容均通过后才计有效。接收器不借助另一侧已恢复内容重建本侧数据。

下例对应板端 `b2z_capacity_start? 2301 500 100 0 0`。先启动两接收器，再发串口命令；如该run_id已使用，三处同步换新编号。新固件须先由用户构建上板。

终端A：

```bash
python3 python/exadv_rx/receive.py --run-id 2301 --channels 3 \
  --serial 000000000000000017c467dc2926a0c3 \
  --sample-rate 4000000 --lna 16 --vga 10 --duration 80 --save-iq --quiet
```

终端B：

```bash
python3 python/zigbee_rx/control_receive.py --run-id 2301 --channel 12 \
  --serial 000000000000000017c467dc3348a6c3 \
  --sample-rate 4000000 --lna 16 --vga 10 --duration 80 \
  --expected-packets 100 --save-iq --quiet
```

不要用 `--command-id` 只过滤单任务，也无需启用 `--control-target-id`。记录输出自动进入当前日期与run_id目录。BLE rx.packets.jsonl增加control_record/control_error字段，summary区分PHY有效包与应用记录有效/匹配计数；计数未去重，逐槽唯一值以联合分析为准。IEEE沿用control_unique等计数。

将完整串口日志保存为该轮board.board.log，待接收正常结束后运行：

```bash
python3 python/control_match/plan_analyze.py \
  --experiment-dir python/experiments/20261112_run2301 \
  --run-id 2301 --analysis-id n4_capacity
```

日期按实际归档目录修改。如果存在多次接收，明确使用 --ble-packets / --zigbee-packets 指定同轮文件。分析器复核CAPACITY_CONFIG和逐槽CAPACITY_SLOT，包括实际长度、生成标志、版本、周期及command_id=slot+1；收到的本侧扩展长度与板端配置不符时拒绝产生有效联合结果。输出plan.report.md、plan.summary.json、逐任务/逐槽CSV与波形成本CSV，报告中附字节预算；这覆盖单轮验收，跨配置manifest自动扫描和热力图汇总仍为后续工具任务。

v2容量探针只用于完整内容恢复，未新增执行扩展blob的应用处理器。若开启scheduled/immediate软件处理，会记录decoded后以capacity_decode_only拒绝处理；不能计为执行成功。IEEE自身负载不知道BLE扩展长度，故其记录的ieee_marker_offset_us为null；BLE本侧可从长度得出480+8b µs，联合报告也会按板端配置列出该布局值。这是格式位置差，不能视作实测同步误差。历史N3分析器显式拒绝v2，避免沿用固定472 µs的v1配置。后续如开展v2时间模型，需要另行声明布局配置并验证模型。

本地校验使用真实C生成器输出的v2字节，覆盖零扩展、BLE/IEEE上界、两侧CRC、坏长度、有效CRC但错误填充、std_ble严格解析及板端实际长度不一致；这些属于软件测试，不增加RF实验轮次。接收端此次适配尚无新增空口验证结果。

### 8.2 首轮零扩展工作点2301

1. 先启动第7节终端A和终端B的接收命令，确认两侧均显示采集已启动，没有设备打开失败。

```text
b2z_capacity_start? 2301 500 100 0 0
```

3. 检查启动输出：`run_id=2301`、`version=2`、`attempts=100`、`k=1`、`pdu_payload_bytes=229`，以及 `rf_mode=standard_secondary_ch3`。此命令不需要先执行plan_clear或plan_add，也不要额外执行plan_start。
4. 让板端和两个接收器自然结束。板端发包结束后还会输出大量逐任务、逐槽和逐阶段文本；**接收器退出不代表串口日志已经完整**。至少等到本轮 `CONTROL_TIME_END run_id=2301 slots=100 overflow=0`，并确认串口后续本轮报告已打印完，再关闭日志。
5. 若有异常，保存全部输出和错误，不删除失败轮。提前停止的记录可能不能通过要求完整计划的联合分析，不能改日志中的state伪装成complete。

### 8.3 保存完整板端日志与环境备注

接收器自动创建 `python/experiments/YYYYMMDD_run2301/`，两个终端应输出同一天的同一个实验根目录。无需为采集额外设置EXP_DIR。跨午夜录制时应事先统一显式实验目录，不能仅凭日期推断两份记录属于同轮。

例如实际目录为20261112_run2301，串口临时日志已关闭后，执行：

```bash
cp -n /tmp/n4_run2301.board.log python/experiments/20261112_run2301/board.board.log
```

`cp -n`不会覆盖已有文件；若目标已存在，先核对它是否就是本轮完整日志。把下面的信息写入该目录的 `notes.md`（无须用脚本填写）：

- 本轮角色：N4零扩展/某扫描点/拒绝验证/v1结构参考；是否首次或重复。
- 完整板端命令与两条接收命令、发送大致时刻、接线和功率、设备序列号、增益。
- b/z、计划槽数、周期、固件版本或构建标识、主机git版本及未提交修改情况。
- 接收起止边界、程序错误、截断、设备重连或其他人工操作。

每侧80秒、4 Msps、ci8的IQ约640,000,000字节，双端约1.28 GB；15点约19.2 GB，另加参考轮。保留IQ本地原始文件，不把“文件尺寸正确”当作USB从未丢样的证明。

### 8.4 执行单轮分析并检查交付物

```bash
python3 python/control_match/plan_analyze.py \
  --experiment-dir python/experiments/20261112_run2301 \
  --run-id 2301 --analysis-id n4_capacity
```

若分析目录已存在，保留原结果并改用新的analysis-id（例如n4_capacity_review）。若提示有多个完整capture，用日志对应的实际路径显式指定 `--ble-packets .../rx.packets.jsonl` 和 `--zigbee-packets .../rx.packets.jsonl`，不能随便选最新文件拼接。

检查 `analyses/n4_capacity/` 的：

|产物|检查内容|
|---|---|
|plan.report.md|版本、字节预算、两侧及联合有效解析的分子/分母|
|plan.summary.json|capacity配置、四象限、两侧接收配置和输入哈希|
|plan.slots.metrics.csv|slot 0–99、双方/单侧/双方缺失分布|
|plan.tasks.metrics.csv|100个独立command_id 1–100，K=1，不能误计为同任务重发|
|plan.bursts.csv|primary/secondary的提交和完成、有效波形长度及padding|

首次零扩展重点：

- 板端应计划100槽；检查实际generated、primary_completed和tx_completed，及deadline_miss、dma_timeout、auxptr_dma_window_miss。若未达到完整发送，保留结果并先定位板端问题。
- `CAPACITY_CONFIG` 为BLE/IEEE记录36/36 B、映射176 B、PDU payload229 B；每个built=1的CAPACITY_SLOT实际长度一致。
- 两接收器正常结束，确认有效记录的version=2、扩展长度0、正确run/slot/command。不能只看BLE PHY包数或IEEE FCS数量。
- 目标是两侧独立完整解析、联合报告正常生成。若少量缺失但存在正确双端样本，记录缺失原因并评估是否有采集截断；不能为通过验收删掉失败槽。持续无有效v2记录、长度/CRC/填充系统性错误应先修复后再扫描。
- 零扩展不包含非空扩展数据，因此继续做2302与2303两个边界点，验证非空扩展和两侧最大长度。合法但解码失败的点属于待分析结果，不可默认为超出协议容量。

### 8.7 v1参考和当前流程的终点

v1的224 B历史工作点已有2203等记录，但不是本次同环境的新重复。需要新一轮结构参考时，使用未占用编号（例如2316），同样启动双端100槽/80秒接收，再串口执行：

```text
b2z_plan_clear?
b2z_plan_add? 0 100 0 0
b2z_plan_start? 2316 500 1
```

这轮是v1纯时间更新参考，command_id=0，无控制任务；只比较包布局及逐槽解析，不把其单位成功任务成本或任务成功率与v2的100个独立任务对比。该参考的version、字段语义及5 B固定开销差必须列出，不能声称是严格单因素性能对照。保存并用plan_analyze的run_id=2316分析，capacity字段为空是预期。

完成首轮扫描后先汇总每点预算、四象限和异常，再决定边界复测。当前已实现的是单轮采集与联合分析；跨配置manifest扫描/热力图工具和公平legacy发射/重组对照尚需实现，没有可以直接运行的legacy验收命令。原第3节C的紧凑编码可行性分析仍是下一项必要工作，不能仅做完15点就宣称整个N4完成。
