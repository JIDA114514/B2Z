# Run 1703：独立双接收端时间保持回放

按[预登记方案](../../../../../doc/independent_sync_holdover_experiment_plan.md)在两条独立 HackRF 录制、独立协议解码后，使用各侧历史包拟合 `local_time = a + b × ref_tick`，再用预留的共同包检验两侧对板端计划时间的**相对估计差**。本结果是单轮离线回放，训练包失收由掩码模拟；不是空口绝对同步精度、执行时差或真实失包条件下的已验证性能。

## 原始接收与时间线

| 检查项 | BLE A | IEEE 802.15.4 B |
|---|---:|---:|
| 采样率；录制时间 | 4 Msps；80 s | 4 Msps；80 s |
| 通过各自校验的 1703 时间更新包 | 300/300 个预设槽 | 300/300 个预设槽 |
| 槽号覆盖；重复 | 0–299；0 | 0–299；0 |
| 相邻包间隔偏离计划值的最大绝对值 | 0.918 ms | 0.918 ms |
| 偏离超过 1 ms 的相邻间隔 | 0/299 | 0/299 |

板端最终统计给出 `planned_slots=reached_slots=generated=primary_completed=tx_completed=300`，`deadline_miss=dma_timeout=0`，历时 60.000004 s；`secondary_dma_late_avg_us=80440`、最大 81541 µs。这个 late 字段是相对计划 secondary 起点的 DMA 提交迟到统计，不是实测 RF 起点。两侧各有效解码 300/300 个 DMA 完成槽，联合有效解码 300/300，双方包内共享字段一致 300/300；详见[合并板端统计的控制匹配报告](../control_match_1703_with_board/control.report.md)。最终统计由用户在对话中提供并原样归档于[板端记录](../../board.board.log)，缺少逐槽串口日志。

两条接收摘要均为 `complete`，各处理 320,000,000 个 IQ 样本，缓存高水位均为 2；BLE 有 89,518 个削顶分量，ZigBee 为 0。逐间隔数据见 [timing.qc.csv](timing.qc.csv)，逐槽解码关联见[控制匹配表](../control_match_1703_with_board/control.slots.metrics.csv)。这次没有再看到 1702 轮的几十毫秒级时间轴跳变，但没有采集前后配对的 USB shortfall 计数，不能证明底层绝无漏样。

ZigBee 接收器误设 `--run-id 1702`，实时控制引擎因此报告 `foreign_run=300`、`unique=0`；其逐包记录内的 ID 均为 1703，FCS 和应用校验通过。原始文件留在 1702 目录；本分析显式指定其路径，按包内真实 ID 1703 读取。离线控制引擎重放给出 `decoded=300`、`clock_updated=300`，不会冒充当时实时引擎已正确更新。

## 固定验证集的相对估计差

训练候选位于 0–19 槽；`common` 两侧使用相同偶数槽，`disjoint` 使用 BLE 偶数槽、ZigBee 奇数槽。验证集为 20–299 槽中 `s mod 5 ∈ {2,3,4}` 的 168 个预设槽，均未参与模型拟合。`N` 是每侧使用的历史更新时间包数，不是重发次数。以下单位为 **µs**，分位数在 168 个双方有效验证槽上计算；全部 32 个预登记配置和 5,376 行逐槽结果见 [summary.csv](holdover.summary.csv)、[validation.csv](holdover.validation.csv)。

| 相同 | 冻结约 56 s | 1 | 34.25 | 64.74 | 67.83 | 68.00 | 168/168 |
| 相同 | 冻结约 56 s | 2 | 1.25 | 2.25 | 2.25 | 2.25 | 168/168 |
| 相同 | 冻结约 56 s | 10 | 3.54 | 6.94 | 7.37 | 7.52 | 168/168 |
| 不同 | 冻结约 56 s | 2 | 27,482.75 | 51,965.70 | 54,186.91 | 54,512.62 | 30/168 |

同槽训练使两侧共同经历的包时刻变化在相对差中大幅抵消。不同槽训练在 `N=2` 且冻结时出现大误差：两点跨度太短，包时刻抖动可能被线性拟合当作频率偏差并长期外推；尚无板端实际 RF 起点测量可进一步定因。扩大训练跨度或周期更新缓解了此轮误差；各 `N` 与更新间隔并非单调关系，不能据此挑选一个“最优”配置。共同事件在两台采样时间轴上的原始相对位移从槽 0 至 299 变化约 71.75 µs，仅用于时间线诊断，未用于逐包校准或调整上述模型。

## 结论边界和待补记录

- 这轮可支持：在受控馈线条件下，两条独立软件接收链分别恢复同一包内时间字段；所定义的离线历史包回放能量化不同包训练、训练包数和更新间隔对**相对时间参考估计**的影响。所有 168 个验证槽均真实被双方收到，漏收情形仅是离线掩码。
- 本轮有板端 `CONTROL_PLAN_STATS` 最终汇总，可用 DMA 完成作为发送代理分母：两侧与联合有效解码均为 300/300。缺少 `CONTROL_PLAN_TASK/SLOT` 逐项日志，板端任务命令号由两侧逐包 `command_id=0` 交叉核对；DMA 完成不等于直接测得完整空口发射。板端实际 RF 起点、两机固定接收延迟和采样缺口仍未独立校准。
- 仅一轮结果，且仍是 `same_channel_diagnostic`；不得将微秒级**相对估计差**写成微秒级绝对同步精度、同步执行误差、真实失包性能或完整 exadv 跨信道跟随。

分析程序为 [`python/control_match/holdover_analyze.py`](../../../../../python/control_match/holdover_analyze.py)，输入 JSONL 与 IQ 哈希见 [summary.json](holdover.summary.json)和[IQ 清单](../../captures/iq.manifest.json)。下一轮记录完整板端日志和采样短缺计数，以正确双侧 Run ID 做至少两轮独立重复，并分别保留每轮结果。
